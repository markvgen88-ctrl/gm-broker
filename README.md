# G.M. Broker — Landing Page

Премиальный лендинг кредитного брокера с пошаговой анкетой проверки шансов
на кредит и автоматической отправкой заявок в Telegram и на e-mail.

```
gm-broker/
├── client/     # React + TypeScript + Vite + Tailwind CSS — сам сайт
└── server/     # Node.js + Express — приём анкет, отправка в Telegram и на почту
```

## Стек технологий

| Слой      | Технологии |
|-----------|------------|
| Frontend  | React 19, TypeScript, Vite, Tailwind CSS 4, Framer Motion, React Hook Form, Zod |
| Backend   | Node.js, Express 5, TypeScript, PostgreSQL (Neon), Nodemailer, Telegram Bot API, Docxtemplater |

## 1. Быстрый старт (локальная разработка)

Понадобится **Node.js версии 20 или выше** (рекомендуется 22 LTS) и npm.

### 1.1. Backend

```bash
cd server
npm install
cp .env.example .env
# откройте .env и заполните TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID, SMTP_*, MAIL_TO
# (для CRM и генерации договоров ещё нужны DATABASE_URL / ADMIN_PASSWORD /
# ADMIN_SESSION_SECRET — см. раздел 7, без них сайт всё равно работает)
npm run dev
```

Сервер поднимется на `http://localhost:4000`. Проверить, что он жив:
`curl http://localhost:4000/api/health`.

### 1.2. Frontend

В отдельном терминале:

```bash
cd client
npm install
cp .env.example .env   # по умолчанию уже настроено на локальный backend через прокси
npm run dev
```

Сайт откроется на `http://localhost:5173`. Запросы к `/api/*` автоматически
проксируются на backend (`http://localhost:4000`), см. `client/vite.config.ts`.

## 2. Настройка Telegram

1. В Telegram напишите **@BotFather** → команда `/newbot` → следуйте
   инструкциям и получите **токен бота** (строка вида
   `123456789:AA...`). Вставьте его в `server/.env` как `TELEGRAM_BOT_TOKEN`.
2. Узнайте **chat_id**, куда бот будет присылать заявки:
   - Найдите вашего бота в Telegram (по имени, которое вы задали) и отправьте
     ему **любое сообщение** (например, «привет»). Если хотите получать
     заявки в отдельный чат/канал — добавьте туда бота и напишите там
     что-нибудь (для каналов бот должен быть администратором).
   - Откройте в браузере:
     `https://api.telegram.org/bot<ВАШ_ТОКЕН>/getUpdates`
   - В JSON-ответе найдите блок `"chat": { "id": ЧИСЛО, ... }` — это и есть
     `TELEGRAM_CHAT_ID`. Для личных сообщений id обычно положительный, для
     групп/каналов — отрицательный (например, `-1001234567890`).
3. Вставьте значение в `server/.env` как `TELEGRAM_CHAT_ID`.

По умолчанию бот уже указан в разметке сайта как
[`@GM_Broker`](https://t.me/GM_Broker) — при необходимости поменяйте ссылку
в `client/src/components/layout/Footer.tsx`.

## 3. Настройка почты (SMTP)

В `server/.env` укажите параметры вашего почтового ящика:

```env
SMTP_HOST=smtp.mail.ru
SMTP_PORT=465
SMTP_USER=your-sender@mail.ru
SMTP_PASS=пароль-или-пароль-приложения
MAIL_FROM=your-sender@mail.ru
MAIL_TO=markvgen@bk.ru
```

Примеры популярных провайдеров:

- **Mail.ru**: `smtp.mail.ru`, порт `465`, требуется включить «Пароли для
  внешних приложений» в настройках безопасности аккаунта.
- **Яндекс**: `smtp.yandex.ru`, порт `465`, тоже требуется пароль приложения.
- **Gmail**: `smtp.gmail.com`, порт `465`, обязательно используйте
  [App Password](https://myaccount.google.com/apppasswords) — обычный
  пароль от аккаунта Google не подойдёт.

Письма с заявками будут приходить на `MAIL_TO` (по умолчанию —
`markvgen@bk.ru`) в виде оформленного HTML-отчёта с полной анкетой клиента.

## 4. Продакшен-сборка

### Backend

```bash
cd server
npm install
npm run build      # компилирует TypeScript в dist/
npm run start       # запускает dist/index.js (нужны реальные переменные окружения)
```

Разверните `server/` на любом Node.js-хостинге (VPS, Render, Railway,
Fly.io и т.д.), задав переменные окружения из `.env.example` в настройках
хостинга (никогда не коммитьте сам `.env` в репозиторий).

### Frontend

```bash
cd client
npm install
VITE_API_BASE_URL=https://api.вашдомен.ру/api npm run build
```

Соберётся статика в `client/dist/` — разместите её на любом статическом
хостинге (Vercel, Netlify, Cloudflare Pages, обычный nginx). Не забудьте:

- Настроить **CORS**: в `server/.env` укажите `CLIENT_ORIGIN=https://вашдомен.ру`.
- Обновить **канонический URL и Open Graph** в `client/index.html` — замените
  все вхождения `https://gmbroker.ru` на ваш реальный домен (5 мест: canonical,
  og:image, og:url, twitter:image, JSON-LD).
- Обновить домен в `client/public/robots.txt` и `client/public/sitemap.xml`.

## 5. Логика анкеты

Вся логика пошаговой анкеты («Проверка шансов на кредит») описана
декларативно в виде графа узлов в файле:

```
client/src/data/questionnaire.ts
```

Граф восстановлен из предоставленной логической карты (XMind) — учтены все
три ветки («Физлицо», «ИП», «ООО»), все условные переходы, точки схождения
вопросов и тупиковые сценарии отказа. Ключевые особенности сценария:

- **Физлицо** — после вопроса о просрочках сценарий расходится на две ветки:
  «чистую» (просрочек не было) с более коротким блоком вопросов о
  недвижимости и «усиленную» (есть/была просрочка), где дополнительно
  проверяются арест на регистрационные действия и наличие автомобиля, а при
  отсутствии дохода или подходящего залога анкета заканчивается отказом
  (узлы с `kind: "decline"`).
- **ИП/ООО** — сначала уточняется дата открытия/регистрации бизнеса (поле
  `inputType: "date"`). Если бизнесу меньше требуемого срока (6 мес. для ИП,
  12 мес. для ООО), клиенту предлагается альтернатива — рассмотрение как
  физлицо (для ИП) или кредитование под залог (для ООО); при отказе от
  альтернативы анкета также заканчивается отказом. Ветвление по дате задаётся
  полем `dateBranch` на узле `input` и вычисляется на клиенте в
  `InputStep.tsx` (см. `fullMonthsSince` в `lib/utils.ts`).
- **Отказные экраны** — отдельный тип узла `DeclineNode` (`kind: "decline"`):
  показывает сообщение и рекомендацию, но не собирает контакты и не
  отправляет анкету брокеру — в отличие от `FinalNode` (`kind: "final"`),
  где клиент оставляет способ связи и заявка уходит в Telegram/на почту.

Чтобы изменить формулировки вопросов, варианты ответов или порядок шагов —
правьте этот файл; движок мастера (`client/src/hooks/useWizard.ts`) и
UI-компоненты (`client/src/components/wizard/`) работают с любым корректным
графом автоматически, без изменения кода.

Человекочитаемые подписи полей для отчёта, отправляемого брокеру, дублируются
в `server/src/lib/fields.ts` — при добавлении новых полей анкеты обновите
оба файла.

## 7. CRM (страница `/admin`)

На сайте есть закрытая страница `/admin` — список всех заявок с сайта, смена
статуса сделки, комментарии по каждому клиенту и генерация договора прямо
из карточки заявки (см. раздел 7.1). База — внешний managed Postgres (Neon
или любой другой Postgres-совместимый провайдер), без привязки к хостингу
сайта. Подробная пошаговая настройка с нуля — в `server/CRM_SETUP.md`.

### Как это устроено

- **Каждая заявка сохраняется в CRM автоматически** при отправке анкеты —
  это происходит независимо от Telegram/Email/Google Sheets, поэтому заявка
  окажется в `/admin`, даже если остальные каналы уведомлений в моменте
  недоступны. Если `DATABASE_URL` не задан — сайт продолжает работать как
  раньше (Telegram/Email не затронуты), просто `/admin` отвечает «CRM ещё
  не настроена».
- **Вход по паролю** — один общий пароль на весь доступ, задаётся
  переменной окружения `ADMIN_PASSWORD` (не хранится в коде). Сессия — JWT
  в защищённой (`httpOnly`) cookie на 30 дней, подписывается секретом
  `ADMIN_SESSION_SECRET`.
- **На странице `/admin`**: список заявок (по убыванию даты), фильтр по
  статусу, карточка заявки с полной анкетой клиента, лентой комментариев
  (каждый — со своей меткой времени) и историей договоров.
- Статус сделки — обычный текст, не фиксированный список: в интерфейсе есть
  подсказки (Новая заявка → В работе → Документы собраны → Отправлено в
  банк → Одобрено / Отказ банка / Клиент отказался → Сделка закрыта), но
  можно вписать и свой вариант — он тоже сохранится и станет доступен как
  фильтр. Подсказки заданы в двух местах: `server/src/lib/statuses.ts` и
  `client/src/data/adminStatuses.ts` (синхронизируются вручную).

### Настройка

Подробная пошаговая инструкция (создание базы в Neon, генерация пароля и
секрета, переменные окружения) — в `server/CRM_SETUP.md`. Коротко: в
`server/.env` (или в переменных окружения хостинга) нужны три значения —
`DATABASE_URL`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`. Таблицы
(`applications`, `application_comments`, `contracts`, `contract_counter`)
создаются автоматически при первом запуске сервера — отдельного шага
миграции нет.

⚠️ Ни одно из этих значений не должно попадать в git — `.env` уже добавлен
в `.gitignore`.

### 7.1. Договор из карточки заявки

Раньше договор с клиентом заполнялся через отдельного Telegram-бота на
отдельном сервере. Теперь это часть CRM — кнопка **«Заполнить договор»**
на карточке заявки:

```
client/src/data/contractQuestionnaire.ts              # Сценарий анкеты — поля по ФЛ/ИП/ООО + общие
client/src/components/admin/ContractWizardModal.tsx   # Сама пошаговая анкета
client/src/components/admin/ContractHistory.tsx       # История договоров на карточке заявки
server/src/lib/contractValidation.ts                  # Валидация введённых данных (zod)
server/src/lib/contractTemplate.ts                     # Сборка .docx из шаблона (docxtemplater)
server/src/assets/template_with_placeholders.docx      # Сам шаблон договора
server/src/db/contracts.ts                              # Счётчик номеров + история по заявке
```

Как это работает:

1. В модалке выбирается тип заказчика (ФЛ / ИП / ООО), дальше — по одному
   вопросу на шаг (паспортные данные для ФЛ, банковские реквизиты, сумма
   кредита, процент вознаграждения) — набор полей идентичен тому, что
   раньше спрашивал Telegram-бот.
2. После проверки на экране сводки данные уходят на сервер
   (`POST /api/admin/applications/:id/contracts`), заполняется `.docx` по
   шаблону через `docxtemplater`/`pizzip` и сразу скачивается.
3. Договор попадает в историю на карточке заявки — оттуда его можно
   скачать повторно в любой момент
   (`GET /api/admin/contracts/:id/download`). Сам файл в базе не хранится —
   при каждом скачивании он собирается заново из сохранённых данных
   анкеты, это гарантирует, что файл всегда соответствует актуальному
   шаблону.
4. Номера договоров — сквозной счётчик в таблице `contract_counter`,
   продолжающий нумерацию старого Telegram-бота (последний номер, выданный
   ботом, — 1492; первый номер, выданный сайтом, — 1493).

Если нужно поменять состав вопросов — правьте
`client/src/data/contractQuestionnaire.ts`; серверная валидация
(`contractValidation.ts`) и сборка `.docx` (`contractTemplate.ts`)
синхронизированы с ним вручную — при изменении набора полей обновите все
три файла.

В самом файле шаблона (`template_with_placeholders.docx`) нет плейсхолдеров
под ИНН/КПП — их не было и в старом боте (он их спрашивал, но никуда не
вставлял). Код готов их подставить (`{{CLIENT_INN}}` / `{{CLIENT_KPP}}`),
если добавить эти плейсхолдеры в сам файл шаблона вручную через Word.

Старый Telegram-бот для договоров (на отдельном сервере) эта функциональность
полностью заменяет — его можно отключать. При отключении стоит отозвать его
токен через **@BotFather**, так как он хранился открытым текстом в коде бота.
